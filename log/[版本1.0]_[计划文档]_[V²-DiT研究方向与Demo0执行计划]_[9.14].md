# V²-DiT 研究方向与 Demo 0 执行计划

> 版本：1.0  
> 日期：2026-09-14  
> 状态：已确认，供下一次会话直接执行  
> 说明：本文中的 **V²-DiT（Vote-and-Verify DiT，投票—验证扩散模型）是本项目提出的研究方案名称，不是已经成熟的现成模型**。

## 1. 一句话目标

给定一张 Minecraft 场景的首帧和一条相机运动轨迹，让视频扩散模型生成相机沿该轨迹运动的视频；在模型内部加入一个“投票—验证”模块，使当前视频帧只从首帧中读取与同一运动规律相符、且经过验证的内容，从而减少建筑变形、纹理漂移、重复结构错配和遮挡处复制错误。

## 2. 已确定的研究边界

### 2.1 最终任务

输入：

1. 同一静态三维场景的首帧图像；
2. 目标视频的相机轨迹；
3. 视频扩散所需的常规条件，例如文本提示、帧数和分辨率。

输出：

- 一段与首帧外观一致、相机运动符合给定轨迹的视频。

主要研究对象是**相机运动造成的背景相对运动**。Minecraft 中自然出现的动物或其他生物可以保留，用于观察模块面对独立运动物体时会发生什么，但第一阶段不以它们为定量指标，也不声称已经解决通用动态场景。

### 2.2 当前不做的方向

- 暂停交比约束方向；
- 不再用程序合成二维图片来模拟近景、远景和飞鸟运动；
- Demo 0 不训练完整视频生成模型，也不以视频观感作为唯一判断；
- Demo 0 不要求先完成相机轨迹导出；
- 第一版运动假设只使用二维平移 `(dx, dy)`，暂不加入旋转、缩放、单应性、三维刚体运动或语义形状库。

这些限制用于先回答一个最关键的问题：**“投票—验证”是否真的比普通特征匹配更容易找到正确的首帧来源，并拒绝错误来源？**

## 3. V²-DiT 到底在做什么

### 3.1 通俗解释

假设当前帧中有一小块“窗户”。普通注意力会在首帧的所有小块中寻找看起来像窗户的部分。楼上、楼下有许多一样的窗户时，它可能读错。

V²-DiT 增加两步：

1. **投票**：每个候选对应关系都会提出一个运动意见。例如“当前这块对应首帧左边 3 格、上边 1 格的位置”，即投给位移 `(3, -1)`。
2. **验证**：检查这个意见是否也得到周围墙面、屋檐、柱子等大量局部区域支持，是否与邻近帧一致，是否可能已经被遮挡。只有通过验证的候选才能把首帧内容送入当前帧。

“票”不是整数选票，也不是像素在预设图形库中挑形状。它是一个候选对应关系所隐含的运动向量，以及该候选的相似度和可信度。

### 3.2 token、像素和投票者

模型不会逐个处理原始像素。图像先被 VAE 和 patch embedding 压缩成规则网格上的 token。一个 token 对应原图中的一块区域；它通常不是一个像素，其真实感受野也可能比显示出来的方框更大。

- **投票者**：当前帧 token 与首帧候选 token 构成的候选对；
- **投票内容**：两者在 token 网格坐标上的位移 `(dx, dy)`；
- **被投票对象**：少量共享运动假设，例如“整面墙大约向右移动 3 格”；
- **投票结果的用途**：生成一个稀疏读取掩码，限制当前 token 可以从哪些首帧 token 读取实际内容。

一个 token 内如果同时包含鸟和天空，单个 token 确实可能混合两种运动。软投票可以表达不确定性，却不能恢复 token 内已经混合掉的细节。这是本方法的明确能力边界，后续只能通过更细的 token、分层特征或对象级模块改善。

### 3.3 每个扩散步中的计算流程

在某个扩散步 `t`，记：

- 当前视频 token：`X ∈ R^(N×C)`；
- 首帧参考 token：`R ∈ R^(M×C)`；
- `N`、`M` 为 token 数量，`C` 为通道数。

扩散模型并不是把上一步的内部 token 原封不动地保存下来。调度器先得到新的带噪潜变量 `z_t`，去噪网络在本次调用中重新将其变成 token。V² 模块在本次去噪网络内部工作，并影响本步的噪声或速度预测；调度器据此得到 `z_(t-1)`，下一步再重复。

具体流程如下。

#### A. 只计算候选分数，先不搬运首帧内容

```text
S = Q(X) K(R)^T,     S 的形状为 [N, M]
```

`S[j,i]` 表示当前 token `j` 与首帧 token `i` 的外观相似程度。此时只比较 `Q` 和 `K`，还没有用 `V(R)` 把首帧内容送过来。

#### B. 每个当前 token 只保留前 L 个候选

初始设定 `L = 8`：

```text
candidate_id, candidate_score: [N, L]
```

这一步删除绝大多数显然无关的候选。

#### C. 候选对提出运动意见

若当前 token 网格中心是 `p_j`，首帧候选 token 中心是 `p_i`，则候选对应关系提出：

```text
d_ji = p_j - p_i = (dx, dy)
```

所以每个候选对产生一个二维运动向量，整体形状为 `[N, L, 2]`。

#### D. 把大量意见软聚合成少量运动假设

初始设定 `K = 4`，同时保留一个“拒绝”槽。用可微的 soft-EM 或 slot-style 迭代聚类得到：

- 运动假设 `μ_k = (dx_k, dy_k)`；
- 每个候选属于各运动假设或拒绝槽的软概率 `[N, L, K+1]`。

这里不是把全体分数降序后直接选最高项，也不是按展平后的 token id 聚类。token id 相邻不一定代表图像中邻近，因此空间一致性必须使用真实的二维 token 网格坐标。

#### E. 验证候选

验证分数由以下信息共同决定：

1. 当前 token 与首帧候选的外观相似度；
2. 候选位移与某个共享运动假设的残差 `||d_ji - μ_k||`；
3. 二维空间邻域是否支持同一运动，且是否跨越明显特征边界；
4. 多帧情况下，运动在时间上是否连续；
5. 候选是否可能被遮挡、移出画面或因重复纹理而无法确认。

验证输出候选的保留权重、拒绝概率和置信度。相似窗户的排除依靠“整个窗户周围的墙、边框、屋檐是否共同支持相同位移”，而不是要求模型先识别“这是窗户”。无穷重复的草地仍可能没有唯一答案，此时正确行为是降低置信度或拒绝。

#### F. 只让验证通过的首帧内容进入当前 token

```text
W_ji ∝ exp(S_ji) × verified_mask_ji
Y_j  = Σ_i W_ji V(R_i)
X'_j = X_j + g_t W_o Y_j
```

这就是“限制信息流”的准确位置：即使前面为了找候选计算过较大范围的 `QK` 相似度，真正携带首帧外观的 `V(R_i)` 只有通过验证后才能被加到当前 token。`g_t` 是随扩散步变化的门控；高噪声阶段先弱一些，中后期再加强。

### 3.4 优化对象和训练范围

Demo 0 先训练或拟合以下新增参数：

- 运动假设聚合器；
- 验证/拒绝打分器；
- 输出投影和扩散步门控；
- 必要时使用低秩适配器。

基础特征编码器或视频扩散主干先冻结。只有 Demo 0 明确优于普通匹配后，才进入视频生成模型：先冻结主干训练 V² 模块，再视结果决定是否解冻少量相邻层。第一阶段不全量训练 VACE 或 CamI2V。

## 4. 模型选择

### 4.1 主线选择：CamI2V

最终首选 CamI2V 作为生成主干和主要 baseline，因为它原生面向“首帧 + 数值相机轨迹 → 视频”，与本项目最终任务直接一致。正式生成实验至少比较：

1. 原始 CamI2V；
2. CamI2V 继续训练相同步数；
3. CamI2V + 等参数量普通 adapter；
4. CamI2V + V² 模块。

第 2、3 项用于排除“多训练了一会儿”或“只是多了参数”带来的提升。

### 4.2 VACE 的位置

VACE 可以作为后续迁移主干，但原始 VACE 没有与 CamI2V 等价的数值相机位姿入口。若使用 VACE，公平比较方式为：

1. VACE + 同一个相机轨迹编码器；
2. VACE + 同一个相机轨迹编码器 + V² 模块。

Demo 0 不依赖完整 VACE，也不在本机 CPU 上部署大模型。先用冻结的图像/VAE特征验证对应关系和信息筛选，避免在核心假设未成立前付出大模型下载和训练成本。

## 5. 预计 Demo

### 5.1 Demo 0：对应关系与运动假设验证器

输入一段 Minecraft 短视频或一对帧。系统不生成新视频，先回答：

- 当前帧的某个 token 在首帧中最可能对应哪里？
- 它属于哪个运动假设？
- 这个对应是否应当被拒绝？
- 在近景、远景、重复窗户、遮挡和运动生物出现时，结果是否合理？

Demo 0 包含两套用户可直接查看的可视化，详见第 8 节；同时运行第 9 节的定量评价。

### 5.2 Demo 1：模块影响当前去噪步

将 V² 插入一个冻结的扩散去噪网络，在不同噪声等级下比较：

- 普通首帧 cross-attention 的信息读取；
- V² 验证后的稀疏信息读取。

观察当前去噪预测、重建特征和跨帧传播是否更稳定。此阶段仍可不生成长视频。

### 5.3 Demo 2：首帧和相机轨迹生成视频

在 CamI2V 中插入 V² 模块，输入首帧和相机轨迹，生成完整视频。目标现象包括：

- 建筑轮廓和局部纹理不随相机移动而漂移；
- 近景、远景产生合理的不同位移；
- 重复窗户或方块不被错误复制到相邻位置；
- 遮挡和新显露区域不过度搬运首帧内容；
- 自然运动的生物不明显拖影、复制或黏在背景上。

最后一项在本阶段仍以人眼观察为主。

## 6. Minecraft 数据计划

### 6.1 为什么选择直接录制 Minecraft

Minecraft 可以同时提供真实三维透视、多层深度、遮挡、重复结构、运动相机和自然运动生物。它比二维图片程序更接近实际视频，也便于重复同一相机路径并导出额外缓冲区。

大量相似方块不是单纯缺点：重复窗户和柱子适合作为匹配歧义压力测试。但一望无际的草地在纯外观上可能确实无法唯一对应，因此不作为主要 top-1 准确率区域，而用于观察置信度和拒绝机制是否诚实。

### 6.2 已知本机环境

- HMCL：`D:\Mc\HMCL-3.16.3.exe`
- 游戏目录：`D:\Mc\.minecraft`
- 当前实例：`D:\Mc\.minecraft\versions\26.1.2`
- 当前实例是 vanilla，主类为 `net.minecraft.client.main.Main`
- 当前尚未配置 Fabric 和实例 mods 目录
- 该版本需要 Java 25

账号验证方式不决定能否加载客户端模组。本项目只配置本地客户端录制与数据导出，不修改账号验证逻辑。

### 6.3 推荐采集栈

下一会话真正开始采集时，先复制一个隔离实例，例如 `26.1.2-V2DiT-Data`，再安装：

1. Fabric Loader；
2. 对应 26.1.2 的 Fabric API；
3. Flashback 0.43.x 的 26.1.x 兼容版本，用于录制 replay、编辑平滑相机路径、导出视频帧和深度图；
4. Mod Menu，可选；
5. 一个很小的自制 Fabric companion logger，按帧写出 `frame, x, y, z, yaw, pitch, roll, fov`。

官方现成功能可以处理 replay、路径和深度图，但没有确认存在直接导出每帧位姿 CSV 的稳定按钮，所以 companion logger 作为正式定量阶段的补充方案。

### 6.4 何时需要相机轨迹

Demo 0 的第一轮热力图和人眼检查不需要相机轨迹，只需要帧对和已知 token 网格。相机轨迹在以下环节才必要：

- 生成精确或近似的背景真值对应；
- 将相机运动与物体独立运动分开；
- 作为 CamI2V 最终生成条件；
- 检查模型预测的运动假设是否符合已知相机运动。

因此先完成 Demo 0 的数据接口、匹配器和可视化，再配置完整 MC 采集链路，避免提前录出格式不适用的数据。

### 6.5 场景组

Demo 0 使用纯 Minecraft 录屏，不做二维程序合成。计划六组：

| 组别 | 场景 | 主要问题 |
|---|---|---|
| A | 唯一纹理的静态建筑，小幅横向相机运动 | 基本对应能否找准 |
| B | 重复窗户、柱子、相似方块 | 是否被相似外观误导 |
| C | 近处栅栏/树、中景建筑、远山/天空 | 是否发现多种位移而不是一种全局位移 |
| D | 相机经过树、柱子或墙角 | 遮挡、新显露区域能否拒绝错误搬运 |
| E | 静态背景 + 运动相机 + 自然运动生物 | 背景定量，生物定性观察 |
| F | 大面积草地、低纹理、低重叠或多种困难组合 | 置信度和拒绝机制压力测试 |

首轮建议每组录 10 个短片，每个短片 17 帧；从首帧与第 5、9、13、17 帧组成不同运动幅度的帧对。正式验证时再扩充到每组 50–100 个短片，并让训练场景与测试场景中的建筑或世界彼此分开。

### 6.6 生物和背景掩码

不要求手动控制生物轨迹。正式定量时，优先用同一个 replay 和同一相机路径渲染两遍：

1. 正常 RGB，包含实体；
2. 隐藏实体的背景版本。

两者差异可近似得到实体和相关遮挡掩码。背景指标排除这些区域，生物区域只做单独的人眼观察。若之后能由 companion mod 导出实体 ID/分割缓冲区，则用它替代图像差分。

## 7. Demo 0 的数据与张量接口

### 7.1 最小输入

第一轮只要求：

```text
clip_id/
  frames/000000.png ...
  metadata.json
```

`metadata.json` 至少记录帧率、原始宽高、帧数和首帧编号。相机位姿、深度、实体掩码允许先为空。

正式定量版本增加：

```text
  camera.csv
  depth/000000.exr ...
  entity_mask/000000.png ...
  visibility/...
```

### 7.2 模型中间结果

为避免保存完整的 `[扩散步, 帧, N, M]` 稠密注意力矩阵造成巨大存储，只缓存可视化和评价所需的稀疏结果：

```text
topl_index       [S, T, N, L]
topl_weight      [S, T, N, L]
slot_assignment  [S, T, N, L, K+1]
reject_prob      [S, T, N]
motion_vectors   [S, T, K, 2]
token_confidence [S, T, N]
```

其中 `S` 为记录的扩散步数，`T` 为帧数。还需保存原图尺寸、VAE 下采样倍率、patch 大小、token 网格高宽、模型层编号和注意力头聚合方式。若需要查看某个查询 token 的完整稠密分布，由后端按需重新计算或只保存选定样本。

## 8. 两种热力图查看方式

热力图只用于解释算法，不参与最终评分。评价代码读取原始预测张量，不能从涂色图片反推指标。

### 8.1 方式一：可交互前后端

实现一个本地网页工具。

#### 后端

使用 FastAPI + PyTorch，负责：

- 列出实验 run、视频、帧、已记录扩散步、模型层和 token 网格；
- 接收 `frame_id`、`diffusion_step`、`token_id`，也允许用户直接点击图像选择 token；
- 返回当前帧中该 token 的名义像素区域；
- 返回该 token 在首帧所有候选 token 上的热力图；
- 返回 top-L 候选列表、权重、候选坐标和位移；
- 返回 K 个运动假设、软归属概率、最终选中假设、拒绝概率和置信度；
- 若有真值，对比预测对应位置和真值位置；
- 可选返回某一层、某一注意力头或多头平均结果。

#### 前端

使用 React/Vite，至少包含：

1. run 和视频选择器；
2. 帧数滑块；
3. 扩散步选择器；
4. token id 输入框，以及在当前帧上点击 token 的功能；
5. 当前帧视图：用边框或半透明色显示所选 token 对应的名义图像块；
6. 首帧视图：显示该 token 对首帧 token 的对应热力图和 top-L 标记；
7. 运动假设面板：显示每个 `(dx,dy)`、得票/软权重、验证分和拒绝概率；
8. 候选表：首帧 token id、位置、相似度、假设归属、验证后权重；
9. overlay 透明度、top-k 数量和图层/注意力头选择控件。

页面必须明确区分：

- token 的**名义像素方框**；
- token 可能更大的**真实感受野**；
- “最像的候选”与“验证后允许读取的候选”。

### 8.2 方式二：与视频等长的逐帧 overlay

对长度为 `T` 的视频输出恰好 `T` 张 overlay 图片，并额外编码一份同长度 MP4 预览。

每个当前帧 token 按最终运动假设涂色：

- 同一个运动假设在连续帧中保持同一种颜色；
- 图例显示颜色、slot id、`(dx,dy)` 和平均置信度；
- 拒绝或低置信区域使用黑色、灰色或高透明度；
- 第 0 帧使用“参考/零位移”颜色；
- 可同时输出两种配色：离散 slot 颜色，以及光流式颜色（色相表示方向、饱和度或亮度表示位移大小）。

不同帧的运动槽没有天然固定编号，因此相邻帧之间按运动向量和槽特征做 Hungarian matching，稳定颜色，避免同一种运动在视频中不断换色。

输出目录至少包含：

```text
overlays/000000.png ...
overlay_preview.mp4
slot_id.npy
slot_prob.npy
reject_prob.npy
motion_vectors.npy
legend.json
```

## 9. Demo 0 评价方案

### 9.1 有几何真值时的原始指标

- **PCK@1 token**：预测位置落在真值 1 个 token 半径内的比例；
- **PCK@2 token**：落在 2 个 token 半径内的比例；
- **Top-8 Recall**：真值是否出现在 8 个候选中；
- **EPE**：预测对应位置与真值对应位置的平均/中位端点误差，同时报告 token 和像素单位；
- **Reject Precision / Recall / F1**：对遮挡、出画和无法可靠对应区域的拒绝质量；
- **Background Warp Error**：在有效可见背景掩码内，用预测对应关系回采首帧特征后得到的特征或 RGB 误差；
- 分别报告唯一纹理、重复结构、多深度、遮挡和低纹理子集。

### 9.2 推荐的固定加权总分

所有分量归一到 `[0,1]`，总分越高越好：

```text
Demo0-Score =
    0.30 × PCK@1
  + 0.15 × Top8Recall
  + 0.20 × exp(-EPE_token / 2)
  + 0.20 × RejectF1
  + 0.15 × exp(-FeatureWarpError / τ)
```

`τ` 使用 baseline 在独立校准集上的 Feature Warp Error 中位数，并在最终测试前冻结。总分用于快速排序，论文或报告中必须同时保留所有原始指标，尤其是各场景子集结果。

### 9.3 暂无相机位姿和深度时

仅使用循环一致性误差、特征 warp 误差和少量人工点作为弱代理。此时可以做模型调试和相对比较，但结果标记为 **provisional**，不与有几何真值的 `Demo0-Score` 混用，也不能声称得到精确对应准确率。

### 9.4 运动生物的观察表

运动生物不计入背景总分，单独记录：

- 是否被错误吸附到背景运动；
- 是否出现复制、拖影或身体撕裂；
- 运动方向是否大体合理；
- 遮挡前后是否出现明显跳变。

## 10. Baseline 与消融实验

Demo 0 至少比较：

| 编号 | 方法 | 用途 |
|---|---|---|
| B0 | 冻结特征的最近邻 / 原始 QK Top-1 | 最简单匹配基线 |
| B1 | 普通 cross-attention | 检查仅用注意力会怎样 |
| B2 | 每个 token 独立预测二维运动，不共享假设 | 检验“共同投票”是否有价值 |
| B3 | QK 候选 + 普通 soft k-means，无学习验证器和拒绝槽 | 检验收益是否只来自聚类 |
| B4 | 与 V² 参数量相近的普通 adapter | 排除增加参数本身的影响 |
| B5 | 完整 V²：候选、软投票、验证、拒绝、稀疏 value 路由 | 本项目方法 |

对 B5 做以下消融：

- 删除拒绝槽；
- 删除二维邻域一致性；
- hard top-1 替代软归属；
- 只做事后热力图，不限制 `V(R)` 信息流；
- `K = 2 / 4 / 8`；
- `L = 4 / 8 / 16`；
- 不同扩散噪声等级和不同插入层。

只有 B5 在多深度、重复结构和遮挡组中稳定优于 B1–B4，并且不明显损害 A 组简单场景，才进入完整视频模型集成。

## 13. 停止或转向条件

出现以下任一情况时，不直接扩大训练规模：

1. V² 只在唯一纹理场景有效，在重复结构、多深度或遮挡场景不优于普通 cross-attention；
2. 提升完全可由等参数普通 adapter 或 soft k-means 解释；
3. 热力图看似成团，但真实 PCK、EPE、拒绝 F1 或 warp error 没有提升；
4. 稀疏 value 路由使简单场景明显退化；
5. 模块只能记住训练世界或建筑，换世界后失效；
6. 在合理 token 分辨率下，大量关键区域始终是不可分离的混合运动 token。

对应处理依次为：调整验证信息与 token 尺度、缩小论文主张、改用更强几何条件，或停止 V² 主线。不能用更长视频和更大模型掩盖 Demo 0 未成立的问题。
