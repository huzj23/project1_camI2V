# [版本1.2] [汇报] CamI2V从DynamiCrafter到极线注意力的完整数据流

日期：2026-09-19

本报告回答两个问题：

1. CamI2V论文使用的baseline到底是什么模型，它原来怎么从一张图生成一段视频。
2. CamI2V到底加了什么模块，这个模块在哪里生效，为什么它和我们“把候选token/运动信息注入扩散模型”的想法有关。

- CamI2V官方仓库：https://github.com/ZGCTroy/CamI2V
- DynamiCrafter官方仓库/权重来源：https://github.com/Doubiiu/DynamiCrafter
- CamI2V官方权重来源：https://huggingface.co/MuteApo/CamI2V

## 0. 先给一句话版

CamI2V的baseline是DynamiCrafter 256x256版本。DynamiCrafter原本会用“首帧图像 + 文本”生成16帧视频，但它不知道相机轨迹，所以容易把相机运动、物体运动、画面纹理混在一起。

CamI2V不是重新训练一个全新视频模型，而是在冻结的DynamiCrafter上加一个相机控制插件。这个插件做两件事：

1. 把给定相机轨迹变成每个像素的6维相机射线特征，也就是Plucker ray embedding。
2. 在U-Net的时序注意力块里，加一条“极线注意力”分支：当前token不是随便看全视频的所有token，而是优先看由相机几何允许的那些token。

这和我们的方向很接近：它也是在扩散模型内部改注意力范围。不过CamI2V用的是已知相机几何；我们想用的是运动投票得到的候选token集合。

## 1. 几个词先说清楚

这些词非常容易混：

### 1.1 RGB像素

原始输入图像是普通图片，比如256x256。每个像素有3个数：R、G、B。

一张256x256 RGB图就是：

```text
[3, 256, 256]
```

一段16帧视频就是：

```text
[3, 16, 256, 256]
```

如果加上batch维度，也就是一次处理几段视频，就是：

```text
[B, 3, 16, 256, 256]
```

这里的`B`不是视频内部的东西，只是“这一批有几条样本”。推理时通常`B=1`，表示只生成一条视频。

### 1.2 VAE latent

VAE可以理解成“压缩器 + 解压器”。

它把一张256x256 RGB图压缩成更小的latent图。CamI2V/DynamiCrafter这里使用的是2D VAE，也就是逐帧压缩，不把4帧或16帧一起塞进VAE里压。

一帧：

```text
RGB:    [3, 256, 256]
latent: [4, 32, 32]
```

16帧：

```text
RGB视频:    [B, 3, 16, 256, 256]
latent视频: [B, 4, 16, 32, 32]
```

为什么256变32？因为空间下采样8倍。一个latent位置名义上对应原图约8x8像素。

这里说“名义上”，意思是：坐标上它落在这个8x8格子附近，但它不是简单把这64个像素平均一下。VAE里面有多层卷积，所以一个latent位置实际会受到周围更大区域影响。

### 1.3 U-Net feature token

扩散模型真正反复计算的是U-Net。U-Net会把latent变成不同分辨率的特征图。

256模型的初始latent是32x32。U-Net里面会出现这些空间尺度：

```text
32x32, 16x16, 8x8, 4x4
```

每个尺度上的一个格子，在做attention时会被展平成一个token。比如在32x32尺度、16帧下：

```text
token个数 = 16 * 32 * 32 = 16384
```

注意：这里的token不是文本token，也不是VAE最开始的4维latent点。它是U-Net某一层特征图上的一个时空格子。

## 2. 论文使用的baseline模型

论文主baseline是DynamiCrafter。

本次部署按论文的256x256设置下载：

```text
baseline模型：
/data/raw/huzijian/project1_camI2V/model/baseline_dynamicrafter_256x256/model.ckpt

官方来源：
https://huggingface.co/Doubiiu/DynamiCrafter/resolve/main/model.ckpt
```

DynamiCrafter在CamI2V里承担的是“原始图生视频模型”的角色。它输入一张参考图和一句prompt，输出16帧视频。

官方256配置里的核心参数：

```text
输入分辨率：256x256
视频长度：16帧
VAE latent通道：4
latent空间大小：32x32
U-Net输入通道：8
U-Net输出通道：4
扩散训练步数：1000
推理DDIM步数：论文默认25
文本/图像CFG：7.5
```

为什么U-Net输入是8通道？因为它把两部分拼在一起：

```text
当前有噪latent:        [B, 4, 16, 32, 32]
首帧条件latent重复16帧: [B, 4, 16, 32, 32]
拼接后:               [B, 8, 16, 32, 32]
```

所以baseline其实并不是“只给U-Net文本”。它每一步去噪时，都把首帧经过VAE得到的latent作为额外4个通道喂进去。

## 3. DynamiCrafter从一张图生成视频的数据流

下面按推理顺序讲。先只看baseline，不看CamI2V新模块。

### 3.1 输入

推理时用户给：

```text
首帧图像: [3, 256, 256]
文本prompt: 例如 "a mountain lake ..."
```

官方demo为了复用训练/推理代码，会把首帧复制成一个“假视频”：

```text
[3, 1, 256, 256] -> 复制16次 -> [3, 16, 256, 256]
```

这不是说模型已经有真实16帧。它只是为了取出首帧条件latent。

### 3.2 VAE编码首帧

每一帧独立进入2D VAE。

```text
[B, 3, 16, 256, 256]
-> reshape成 [B*16, 3, 256, 256]
-> VAE encoder
-> [B*16, 4, 32, 32]
-> reshape回 [B, 4, 16, 32, 32]
```

在单图推理里，因为16帧都是复制的首帧，所以这里得到的是16份相同/近似相同的首帧latent。

然后取条件帧，一般是第0帧：

```text
条件帧latent: [B, 4, 32, 32]
重复16次:     [B, 4, 16, 32, 32]
```

### 3.3 文本和图像也走CLIP条件

DynamiCrafter还有另一条条件路线：

1. 文本prompt进入冻结的OpenCLIP文本编码器，得到77个文本token。
2. 首帧图像进入冻结的OpenCLIP图像编码器，得到图像特征。
3. 图像特征再经过Resampler，变成16个图像条件token。

最后拼成：

```text
77个文本token + 16个图像token = 93个cross-attention条件token
```

每个token维度是1024。

也就是说，首帧给模型的信息有两种：

```text
路线A：首帧VAE latent，作为U-Net输入通道拼进去
路线B：首帧CLIP图像token，作为cross-attention条件
```

### 3.4 初始视频不是一帧一帧生成，而是整段一起生成

扩散推理开始时，模型先随机生成一个纯噪声latent视频：

```text
x_T: [B, 4, 16, 32, 32]
```

这里16帧同时存在。不是先生成第1帧，再生成第2帧。

然后DDIM做25轮左右去噪。每一轮都处理完整的16帧latent视频。

### 3.5 每一步U-Net具体吃什么

在某一个扩散步`t`，U-Net拿到：

```text
当前噪声视频latent x_t: [B, 4, 16, 32, 32]
首帧条件latent c_concat: [B, 4, 16, 32, 32]
拼接后输入U-Net: [B, 8, 16, 32, 32]

cross-attention条件:
[B, 93, 1024]

时间步t:
[B]

帧率/stride条件:
[B]
```

U-Net输出：

```text
预测噪声 epsilon: [B, 4, 16, 32, 32]
```

DDIM用这个预测噪声，把`x_t`更新成更干净一点的`x_{t-1}`。

重复25次后，得到最终干净latent视频：

```text
[B, 4, 16, 32, 32]
```

最后逐帧VAE decode：

```text
[B, 4, 16, 32, 32]
-> [B, 3, 16, 256, 256]
```

## 4. Baseline的注意力在哪里发生

DynamiCrafter的U-Net里有两类attention。

### 4.1 空间注意力

空间注意力在单帧内部做。

比如某一层是：

```text
[B*16, C, H, W]
```

它会变成：

```text
[B*16, H*W, C]
```

然后每一帧里的每个位置可以看同一帧里的其他位置。

这类attention负责画面内部结构，例如“桌子和杯子在同一帧里的关系”。

### 4.2 时序注意力

时序注意力沿时间做。

它不是把全视频`16*H*W`一次性展开看全局，而是对每个空间坐标单独看16帧：

```text
同一个(x,y)位置在16帧上的特征 -> 做temporal self-attention
```

也就是说，baseline天然擅长处理“同一画面坐标附近的时间一致性”，但不擅长处理大幅相机运动下的对应关系。

如果相机往右移，一个物体在画面里从左边跑到中间，它不再是同一个(x,y)。baseline的时序注意力不容易把它们连起来。

这就是CamI2V要补的地方。

---

## 5. CamI2V加了什么

CamI2V在baseline上加了三类东西：

```text
1. 相机射线编码器：把相机轨迹变成多尺度特征。
2. Plucker projection：把相机特征加进U-Net时序块。
3. Epipolar attention：让token按极线几何去看其它帧的候选位置。
```

论文说CamI2V比DynamiCrafter多约261M参数，base DynamiCrafter约1.4B参数。

训练时，原始DynamiCrafter主体被冻结，主要训练新增的相机相关模块。

---

## 6. 相机输入是什么

CamI2V不是只给一张图。它还要求给一条相机轨迹。

官方demo的相机轨迹文件里，每一帧有：

```text
相机内参K
相机外参RT / w2c矩阵
```

对256x256输入，demo中相机内参大致按resize/crop后的图像大小构造：

```text
fx = 0.5 * max(resized_H, resized_W)
fy = fx
cx = 0.5 * W
cy = 0.5 * H
```

外参先转成`c2w`，再相对于条件帧做归一化：

```text
relative_c2w[t] = inverse(c2w[cond_frame]) @ c2w[t]
```

直白说：模型看的不是“世界坐标里的绝对相机位置”，而是“从首帧相机出发，每一帧相机相对动到哪里”。

---

## 7. Plucker ray embedding：每个像素一条相机射线

对每一帧、每个像素，CamI2V构造一条从相机中心穿过这个像素的3D射线。

像素坐标用的是图像坐标：

```text
左上角附近是(0,0)
x向右增大
y向下增大
代码里使用像素中心，所以会加0.5
```

某个像素`(u,v)`先通过内参变成相机坐标方向：

```text
[(u - cx) / fx, (v - cy) / fy, 1]
```

再用相机外参旋到世界/相对相机坐标里。

最后每个像素得到6个数：

```text
Plucker ray = [o x d, d]
```

其中：

```text
o = 相机中心
d = 该像素对应的射线方向
o x d = 相机中心和方向的叉乘
```

所以Plucker输入张量是：

```text
[B, 6, 16, 256, 256]
```

这里6不是RGB，也不是latent通道，而是每个像素的几何射线描述。

## 8. 相机姿态编码器怎么把Plucker变成U-Net可用特征

官方256配置里：

```text
downscale_factor = 8
cin = 384
channels = [320, 640, 1280, 1280]
nums_rb = 2
temporal_attention_nhead = 8
```

为什么`cin=384`？

因为输入Plucker是6通道，先做`PixelUnshuffle(8)`：

```text
6 * 8 * 8 = 384
```

也就是把原来256x256的每8x8邻域重新排进通道里，空间大小变成32x32：

```text
[B, 6, 16, 256, 256]
-> 先把B和T合并: [B*16, 6, 256, 256]
-> PixelUnshuffle(8): [B*16, 384, 32, 32]
-> 3x3卷积到320通道: [B*16, 320, 32, 32]
```

然后经过多层ResNet block和时序attention，输出多尺度相机特征：

```text
32x32: [B, 320, 16, 32, 32]
16x16: [B, 640, 16, 16, 16]
8x8:   [B, 1280,16, 8, 8]
4x4:   [B, 1280,16, 4, 4]
```

这些特征会被送到U-Net对应尺度的时序Transformer里。

## 9. 极线注意力：它到底限制了什么

这是CamI2V最关键的部分。

如果我们知道两帧相机的相对位姿，那么第i帧某个像素在第j帧里不可能随便对应到任何地方。它的对应点必须落在第j帧的一条线上，这条线叫极线。

CamI2V用相机内参`K`和相对位姿`R,t`算基础矩阵：

```text
E = [t]_x R
F = K_j^{-T} E K_i^{-1}
```

对第i帧的一个点`p_i`，第j帧的极线是：

```text
l_j = F p_i
```

然后在U-Net某个feature map尺度上，把所有token的位置换算回原图坐标。比如在32x32 latent尺度上，一个格子的中心大约在原图8x8格子的中心：

```text
pix2coord(x, downsample) = x * downsample + downsample / 2 - 0.5
```

如果某个候选token到极线的距离小于半个feature格子的对角线，就允许注意：

```text
distance < downsample * sqrt(2) / 2
```

这就是一个bool mask：

```text
允许看 = True
不允许看 = False
```

如果某层有16帧、H x W个格子，那么mask形状是：

```text
[B, 16*H*W, 16*H*W]
```

也就是每个query token对所有时空token都有一个“能不能看”的开关。

## 10. Epipolar attention的Q/K/V来自哪里

这一点对我们很重要。

CamI2V的极线注意力不是拿RGB颜色算相似度，也不是拿首帧SIFT特征算相似度。它的Q/K/V来自U-Net当前扩散步、当前层的feature。

代码里做的是：

```text
normed_x = LayerNorm(U-Net当前时序块输入特征)
pose_feature = 相机姿态编码器输出的对应尺度特征

epipolar_input = normed_x + pose_feature
```

然后：

```text
Q = Linear(epipolar_input)
K = Linear(epipolar_input)
V = Linear(epipolar_input)
```

再用极线mask限制attention：

```text
attention(Q, K, V, mask=epipolar_mask)
```

所以它做的是：

```text
在扩散模型内部的语义/几何特征上做受限注意力
```

不是：

```text
在原图RGB上直接找最像的像素
```

这和我们后续要改VACE时的启发是：如果要注入运动投票信息，最好注入到U-Net/DiT内部的attention logits或mask里，而不是只在前端RGB上画色块。

## 11. Register token是什么

论文文字写的是2个register token；当前官方256推理配置里写的是：

```text
num_register_tokens: 4
```

这不是我猜的。部署后我直接读了官方 `256_cami2v.pt` checkpoint，确认当前公开256版本里每个极线注意力模块确实是4个register token。参数形状是：

```text
register_tokens: [1, 4, C]
C = 320 / 640 / 1280，随所在U-Net尺度变化
一共16组register_tokens参数
```

所以这里有一个版本差异：论文文字写2个，当前官方配置和当前公开权重实际使用4个。后续复现实验应以配置和checkpoint为准。

register token可以理解成几个“兜底槽”。当极线mask过窄、某些query找不到合适候选，或者几何约束不完整时，模型还能把注意力放到这些学习出来的公共token上。

代码里register token只拼到K/V，不拼到Q：

```text
context = [register_tokens, all_video_tokens]
```

它们对所有query永远可见。

这对我们也有启发：如果未来用运动投票mask限制注意力，最好保留兜底通道，不要把所有不在候选表里的token硬切掉到完全不可见。

## 12. CamI2V模块插入在U-Net哪里

CamI2V通过monkey patch改了DynamiCrafter的U-Net forward。

每个扩散步里，U-Net会经过很多block。CamI2V在TemporalTransformer的BasicTransformerBlock里插入新逻辑。

原始Temporal block大致是：

```text
x = temporal_self_attention(norm1(x)) + x
x = attn2(norm2(x), context) + x
x = FFN(norm3(x)) + x
```

CamI2V改成：

```text
normed_x = norm1(x)

zero_init_x = 0
zero_init_x += pluker_projection(normed_x + pose_feature)
zero_init_x += epipolar_attention(normed_x + pose_feature, epipolar_mask)

x = zero_init_x + temporal_self_attention(normed_x) + x
x = attn2(norm2(x), context) + x
x = FFN(norm3(x)) + x
```

官方256配置里：

```text
add_type: add_to_main_branch
```

所以新增相机分支是加到原始时序attention输出旁边，而不是替代原始时序attention。

这很重要：CamI2V没有把原有注意力废掉。它让模型保留原始能力，同时新增一条相机几何引导分支。

另外，`pluker_projection`和epipolar attention的输出层用零初始化。意思是训练刚开始时，这些新模块输出近似0，模型行为接近原来的DynamiCrafter；训练过程中再慢慢学会使用相机分支。

## 13. 哪些尺度上发生

配置声明极线attention支持：

```text
attention_resolution: [8, 4, 2, 1]
```

这里对应原图下采样比例：

```text
8  -> 32x32 latent尺度
16 -> 16x16尺度
32 -> 8x8尺度
64 -> 4x4尺度
```

但当前公开代码里还有一个实现细节：它用如下条件选择要patch的Temporal BasicTransformerBlock：

```python
_module.context_dim is None
and _module.attn1.to_k.in_features != init_attn[0].proj_in.out_channels
```

这个条件单看源码不够直观，所以我用实际checkpoint把模块名打印出来确认了一遍。当前官方 `256_cami2v.pt` 里实际有16个epipolar attention模块：

```text
input_blocks.1.2.transformer_blocks.0.epipolar   C=320
input_blocks.2.2.transformer_blocks.0.epipolar   C=320
input_blocks.4.2.transformer_blocks.0.epipolar   C=640
input_blocks.5.2.transformer_blocks.0.epipolar   C=640
input_blocks.7.2.transformer_blocks.0.epipolar   C=1280
input_blocks.8.2.transformer_blocks.0.epipolar   C=1280
middle_block.2.transformer_blocks.0.epipolar     C=1280
output_blocks.3.2.transformer_blocks.0.epipolar  C=1280
output_blocks.4.2.transformer_blocks.0.epipolar  C=1280
output_blocks.5.2.transformer_blocks.0.epipolar  C=1280
output_blocks.6.2.transformer_blocks.0.epipolar  C=640
output_blocks.7.2.transformer_blocks.0.epipolar  C=640
output_blocks.8.2.transformer_blocks.0.epipolar  C=640
output_blocks.9.2.transformer_blocks.0.epipolar  C=320
output_blocks.10.2.transformer_blocks.0.epipolar C=320
output_blocks.11.2.transformer_blocks.0.epipolar C=320
```

更通俗地说：它不是只在一个地方改注意力，而是在U-Net下采样、中间层、上采样的多个时序Transformer里都插了极线注意力。低分辨率层看大结构，高分辨率层看局部细节。

## 14. 训练阶段学什么

baseline DynamiCrafter训练时学的是：给定有噪latent、文本/图像条件、时间步，预测噪声。

公式上就是：

```text
x_t = sqrt(alpha_t) * x_0 + sqrt(1-alpha_t) * noise
model(x_t, t, cond) -> predicted_noise
loss = MSE(predicted_noise, noise)
```

CamI2V训练时仍然是同一个扩散损失，但冻结原始DynamiCrafter主体，主要训练新增相机模块：

```text
训练：pose encoder
训练：Plucker projection
训练：epipolar attention
训练：register tokens
冻结：原始DynamiCrafter U-Net主体
冻结：文本编码器
冻结：图像编码器
冻结：图像projection模型
冻结：VAE
```

论文设置：

```text
数据：RealEstate10K
视频长度：16帧
```

## 15. 推理阶段一步一步做什么

以“输入一张图 + 指定相机轨迹”为例。

### 第1步：预处理图像

```text
输入图片 -> resize + center crop -> 256x256
像素范围 [0,255] -> [-1,1]
```

### 第2步：构造条件batch

```text
video: 复制首帧16次得到 [B,3,16,256,256]
caption: 文本prompt
RT: 16帧相机外参 [B,16,4,4]
camera_intrinsics: 16帧相机内参 [B,16,3,3]
frame_stride/fps: 帧率条件
cond_frame_index: 通常为0
```

### 第3步：编码首帧条件

```text
VAE编码 -> 首帧latent条件
CLIP文本编码 -> 文本token
CLIP图像编码 + Resampler -> 图像token
```

### 第4步：编码相机条件

```text
相机RT转相对位姿
每个像素构造Plucker ray
pose encoder输出多尺度相机特征
相机几何计算每个尺度的epipolar mask
```

### 第5步：初始化16帧纯噪声latent

```text
x_T = random normal [B,4,16,32,32]
```

### 第6步：做25轮DDIM去噪

每一轮：

```text
1. 把当前x_t和首帧条件latent拼成8通道。
2. U-Net处理完整16帧latent视频。
3. 空间attention在单帧内部看。
4. 原始时序attention在同一空间坐标跨16帧看。
5. CamI2V新增的epipolar attention在极线允许的位置看。
6. U-Net预测噪声epsilon。
7. DDIM更新x_t到x_{t-1}。
```

### 第7步：VAE解码

```text
最终latent视频 [B,4,16,32,32]
-> VAE decoder逐帧解码
-> RGB视频 [B,3,16,256,256]
```

## 17. 消融实验说明了什么

论文里有几个关键消融：

```text
只用Plucker相机特征：有提升，但不够。
只对条件帧做极线attention：有提升，但弱于全帧极线attention。
全3D attention：比baseline好，但弱于epipolar attention。
没有Plucker只做epipolar：明显变差。
```

这说明：

1. 相机射线特征能告诉模型“相机怎么动”。
2. 极线attention能告诉模型“当前token应该去哪里找跨帧信息”。
3. 只给全局attention并不等于最好，因为全局attention会看到大量无关或带噪token。
4. 最有效的是“相机特征 + 受几何约束的attention”一起用。

## 18. 和我们运动投票方向的关系

我们当前想做的是：根据运动投票，为每个token找一批它应该关注的首帧/尾帧/其他帧token，然后把这些候选注入扩散模型，让注意力不用全图乱看。

CamI2V给了一个很直接的参考：

```text
CamI2V: 用相机几何生成attention mask。
我们:   用运动投票生成attention mask或attention bias。
```

两者的共同点是：

```text
都不是在扩散模型外面后处理视频。
都是在扩散模型内部改attention可见范围/注意力权重。
都希望减少无关token干扰，提高跨帧一致性。
```

不同点是：

```text
CamI2V依赖已知相机轨迹和针孔相机几何。
我们的运动投票更像从视频/图像本身估计候选对应关系。
CamI2V约束的是极线，不直接解决同一极线上的深度二义性。
我们的投票如果做得好，可能在极线或运动假设内部进一步排序具体候选token。
```

对我们最有价值的实现方式不是“另写一个前端投票可视化”，而是：

```text
在U-Net/DiT的某个attention block里，把运动投票候选表变成mask或logit bias。
Q/K/V仍然使用模型内部特征。
候选表只决定哪些位置可见、哪些位置加权更高。
保留原始attention或register token作为兜底。
```

## 19. 对demo0和后续主实验的启发

### 19.1 当前RGB/RootSIFT demo0只能验证候选方向，不能等价于模型内部token

我们之前的demo0用的是图像网格特征，比如RootSIFT/颜色。这可以帮助肉眼看“候选位置是不是大致对”，但它不等价于VACE或CamI2V内部的扩散token。

CamI2V再次说明：真正注入时，候选关系应该作用在扩散模型内部feature token上。

### 19.2 不要直接硬切全局

CamI2V不是删掉原始temporal attention，而是新增一条几何分支。这个设计比较稳。

我们后续如果做运动投票注入，也建议优先考虑：

```text
原始attention保留
运动候选attention作为新增分支
或把运动候选作为soft bias而不是hard mask
保留register/fallback token
```

### 19.3 候选token应该分尺度

CamI2V在32x32、16x16、8x8、4x4等多尺度上工作。我们如果只在一个固定网格上投票，和模型内部实际attention层会错位。

更合理的是为不同U-Net层准备不同尺度的候选表：

```text
32x32层：候选粒度细，接近8x8原图区域。
16x16层：候选更粗，接近16x16原图区域。
8x8/4x4层：候选很粗，更偏全局布局。
```

### 19.4 运动投票可以和相机几何结合

如果数据有相机轨迹，最佳路线可能不是二选一。

可以先用相机几何给出极线候选带，再用运动投票/视觉相似度在极线带内部排序。这样既不会全图乱看，也不会只靠颜色在天空里乱猜。

## 22. 对晚间汇报的建议说法

可以这样讲：

```text
我们调研CamI2V，是因为它已经做了“把几何约束注入视频扩散模型注意力”的事情。

它的baseline是DynamiCrafter。DynamiCrafter用首帧和文本生成16帧视频，但时序注意力主要在同一空间坐标跨帧看，所以遇到明显相机运动时，对应关系不稳定。

CamI2V没有从头训练模型，而是在冻结的DynamiCrafter上加相机分支。它把相机轨迹转成每个像素的Plucker射线特征，并在U-Net时序Transformer里加极线注意力，让每个token只看几何上可能对应的位置。

这说明我们的方向是合理的：如果运动投票能给出可靠候选token，就可以像CamI2V使用极线mask一样，把候选表注入扩散模型attention中。差别是CamI2V的候选来自相机几何，我们的候选来自运动投票和视觉/时序一致性。
```

## 23. 最后给一个非常直白的类比

DynamiCrafter像一个会画视频的人，但他只拿到首帧和文字，不知道摄影机怎么移动。

CamI2V给这个人加了一把尺子：告诉他相机从哪里移动到哪里，并告诉他“这个点到下一帧大概只能沿这条线找，不要满画面乱找”。

我们的运动投票方向，是想再加一个更细的指路牌：不仅告诉他沿哪条线，还告诉他“这几个位置更像是同一个东西，你优先看它们”。
