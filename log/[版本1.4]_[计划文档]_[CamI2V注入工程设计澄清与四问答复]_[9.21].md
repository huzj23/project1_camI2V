### 问题 3 — 运动投票怎么注入 CamI2V

#### 3.1 注入位置：第 4 条零初始化并行分支

CamI2V 现有结构（已逐行核实）：

```python
# lvdm TemporalTransformer 的 BasicTransformerBlock，被 monkey patch 后的 forward
normed_x = self.norm1(x)
zero_init_x  = torch.zeros_like(normed_x)
zero_init_x += self.pluker_projection(normed_x + pluker_feat)          # 分支①相机射线
zero_init_x += self.epipolar(normed_x + pluker_feat, epipolar_mask)    # 分支②极线注意力
x = zero_init_x + self.attn1(normed_x) + x                             # 与原始时序注意力并行相加
x = self.attn2(self.norm2(x), context=context) + x
x = self.ff(self.norm3(x)) + x
```

V² 加第 4 条，形态与①②完全同构：

```python
zero_init_x += self.v2_reference_attention(                            # 分支③ 新增
    q_feat   = normed_x,
    ref_kv   = reference_kv,        # 参考端点（首帧/尾帧）的 K/V
    vote_mask= vote_mask,           # 运动投票产生的稀疏候选掩码 [B, L, M]
    gate     = g(step, confidence), # reject 时为 0
)
```

**为什么必须是"并行相加 + 零初始化"**：
1. 训练/接入初期 `zero_init_x ≈ 0`，模型行为严格等于原 CamI2V → 可随时回退，可做干净的消融；
2. 不替换 `attn1`，符合 [版本1.2] §12 与 [版本1.16] 的结论——CamI2V 自己就是这么做的，不要硬切全局注意力；
3. 与 1.0 计划 §3.3 F 式一致：`X'_j = X_j + g_t · W_o · Y_j`。

#### 3.2 参考 K/V 从哪来：**这是最关键的未决点**

我核对了 `single_image_for_inference.py`，CamI2V 的条件是这样构造的：

```python
ref_img = repeat(ref_img, "c 1 h w -> c f h w", f=16)   # 首帧复制 16 份
# 若给尾帧：ref_img[:, -1:, :, :] = ref_img2            # 第 15 槽替换为尾帧
```

这个"条件视频"经 VAE 编码后进入 U-Net 的 `c_concat`（额外 4 个输入通道）。

**含义**：干净首帧确实存在于网络输入里，但它在**第一个卷积层就被与 noisy latent 融合了**——到了注入点（U-Net 中深层）已经无法分离出"干净参考 token"。

三条可选路线：

| 路线 | 做法 | 优点 | 代价 |
|---|---|---|---|
| **A. 借用当前特征的第 0 帧位置** | 参考 K/V 直接取 `normed_x` 在时间位置 0 上的 token | **零新增参数、立刻可做** | 该位置本身是 noisy 的，"参考"不干净 |
| **B. 新增 reference encoder**（推荐中期） | 仿照 CamI2V 的 `pose_encoder`：单独编码干净首帧 latent → 多尺度 K/V | 参考真正干净，架构对称 | 新增参数与一次额外前向 |
| **C. 从 c_concat 重新解耦** | 在浅层把干净通道单独抽出来走旁路 | 复用已有信息 | 需要改上游 conv 结构，违反 R5 |

S1/S2 用 **A**（只读诊断，够用）；真正注入时用 **B**。

#### 3.3 投票掩码从哪来：**第二个未决点**

Demo0 的投票吃的是"显式图像网格描述子"，CamI2V 里没有这个东西。可选：

- **A. 复用 pose_encoder 特征算候选** —— 与 epipolar 分支同源，成本最低；
- **B. 用 attn1 的真实 Q/K 算候选** —— 最贴近"模型自己认为谁像谁"，但要 hook 每层的 Q/K；
- **C. 外部描述子（RootSIFT 那套）算候选** —— 可复用 Demo0 代码，但回到"外部 token"的老问题。

**建议 A**：理由是候选与参考都用网络内部特征，符合 [版本1.2] §10 的核心结论（Q/K/V 应来自扩散模型内部特征，不是 RGB 直接匹配）。

### 问题 4 — 当前运动投票只考虑平动吗？有转动吗？

**答：只有平动与"径向缩放"，旋转自由度为 0。**

代码证据（[core.py](data/demo0_v11/core.py) 第 333–336 行，全部投票路径的唯一速度模型）：

```python
def _predict_velocity(parameters, position):
    scale_rate  = parameters[:, 0]                    # 标量
    translation = parameters[:, 1:]                   # (tx, ty)
    return position[:, None, :] * scale_rate[None, :, None] + translation[None, :, :]
```

每个运动槽 3 个参数 `(s, tx, ty)`，速度场为：

```text
v(p) = s · p + t
```

- **H0**（`_fit_one_parameter` 中 `value[0] = 0.0`）：`v(p) = t` → **纯平移，2 自由度**
- **H1**（else 分支）：`v(p) = s·p + t` → **平移 + 各向同性径向缩放，3 自由度**

`s · p` 是**用标量乘位置向量**，即一个以原点为中心的**径向伸缩场**——它可以近似表达"透视缩放（近处位移大、远处位移小）"，但：

```text
✗ 没有 2×2 旋转矩阵          ✗ 没有角速度
✗ 没有各向异性缩放（sx ≠ sy） ✗ 没有剪切
✗ 没有单应 / 没有 3D 反投影    ✗ 没有任何旋转相关参数
```

**交叉验证**：对 `data/demo0_v11/` 全部 `.py` 检索 `rot|yaw|pitch|affine|homograph|angle|2x2`，命中的只有两类——

1. `cv2.rectangle`（绘图，"rectangle" 里含 "angle"，纯误命中）；
2. `yaw_deg` / `pitch_deg`，且**只出现在窗口元数据**里（`yaw_range_deg`、`pitch_range_deg`，用于描述"这个窗口相机转了多少度"），**从不进入候选、投票或掩码计算**。

**这与数据不匹配**：

| 数据 | 相机是否存在转动 |
|---|---|
| 转向平动 | **是，且是主要运动** |
| 简单平动透视关系 | 有 yaw/pitch 漂移 |
| 非对称建筑平动 | 去程/回程含转向 |

**后果**：纯转动会让二维位移场**绕消失点旋转**，H0/H1 都无法表达。Demo0 v1.1 在"转向平动"上从未被单独评测过（冻结三窗口没有一段来自它），所以这个缺口一直没有暴露。

**但要注意一个重要的分工**：CamI2V 的极线几何 `F = K_j^{-T} [t]_× R K_i^{-1}` **本身已经精确含旋转 R**。所以有一条更省力的路线：

```text
旋转  -> 交给极线几何（已有，精确）
平动+尺度 -> 交给运动投票（用于在极线带内做精细排序与拒绝）
```

是否需要把旋转加进投票（例如升级到 H2：完整 2D 仿射 / H3：单应），取决于 S2/S3 的结果——如果"极线带内排序"已经是主要瓶颈，那么加旋转收益有限；如果发现同一物体沿极线被系统性错排，就需要 H2。

### 2.3 相机 logger 的一个确定性缺陷

今天 6 次导出，与 `depth_map` 设置**完全相关（6/6）**：

```text
depth_map = True    → CSV 只有表头 207 B，零行数据     （3/3 失败）
depth_map = False   → CSV 完整 257–359 KB              （3/3 成功）
```

**根因**：[FlashbackExportJobMixin.java](mc_tools/v2dit-camera-logger/src/main/java/io/v2dit/camera/mixin/FlashbackExportJobMixin.java) 的第三个 `@Inject` 挂在 `SaveableFramebufferQueue.startDownload(...)` 这个调用点上，一帧采一次。开启深度渲染后 Flashback 的导出循环不再经过该调用点，所以只有 HEAD/TAIL 两个注入生效——文件被创建（有表头）但一行都没写。

**当前不阻塞**：因为同一条数据的 RGB 导出有完整 CSV，而两者 tick 区间一致、渲染确定性，可以配对使用。但**如果以后要单独导深度，必须知道拿不到轨迹**。

### 2.4 深度图精度不足（重要）

以简单平动第 0 帧为例，8-bit 灰度直方图：

```text
0           327,229 px  (35.5%)   ← 天空 / 远裁剪
1                5,806 px
2–128            ~3,000 px
128–192           9,469 px  ( 1.0%)
192–255         125,009 px  (13.6%)
255             451,149 px  (49.0%)   ← 近场几何全部饱和
```

对照 RGB/深度图像可以确认：**建筑、柱子、地面、云全部是纯白 255，没有任何内部层次**；只有远景山丘有灰度梯度。

**结论：这份深度不能用于近场的像素级重投影。** 49% 的像素没有深度信息，而近场正是我们最需要精确对应的地方。

可能的原因（未验证）：Flashback 输出的是透视深度缓冲的 8-bit 量化，透视深度在近场高度非线性，导致近处物体全部压到 255。

**若要修，有三条路**（成本递增，尚未决定走哪条）：

1. **重导深度为 PNG 序列**——去掉 H.264 有损压缩，但 8-bit 的量化问题依旧；
2. **导出时降低渲染距离**——压缩深度动态范围，让近场拿到更多量化级，需实测能改善多少；
3. **体素光线投射**——MC 世界是体素网格，`saves/` 里有存档、CSV 里有逐帧位姿与 FOV，直接光线投射可得**精确深度**。最准，但要解 Anvil/region 格式，工作量最大。
