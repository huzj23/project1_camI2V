# 版本 1.12｜当前投票算法逐项解剖

日期：2026-09-16。以下均指已运行的 D0-Real 算法；其输入是 1.11 文档的手工描述子，不是 VACE Q/K。

## 1. 检索先做什么

对每帧的每个查询 Token `q`，构建参考库：`F` 模式为首帧 1296 个 Token；`FL` 模式为首帧与尾帧共 2592 个 Token。先与库内**全部** Token 计算相似度，而不是只与附近或一个运动槽计算。特征为两个 RootSIFT 加 RGB/Lab 局部颜色的 265 维单位向量；分数为归一化向量的**内积/余弦相似度** `s(q,r)=d_q·d_r`。RGB 不是逐像素差，也没有使用 VAE 潜空间高维张量。排序取 Top-16，留存参考端点、Token ID、原分数；主要交互与 P5 稀疏候选限制到 Top-8。[本地描述子和检索实现](../data/demo0_v11/core.py)、[候选数组生成](../data/demo0_v11/pipeline.py)

所谓“原对应像素-置信度表”需要拆开：P0 存的是**外观相似度 Top-16**，不能称为真实对应像素概率；由 Top-16 分数以温度 `0.012` softmax 得到相对权重，并计算 Top1/Top2 差距与熵。softmax 权重只在这 16 个候选之间归一，不是经过真实对应标签校准的正确率。热力图的全参考库余弦分数又是网页查询时从保存的描述子计算的，与已截断的候选权重是两套数值。[候选统计](../data/demo0_v11/core.py)、[网页热力图计算](../data/demo0_v11/backend/server.py)

## 2. 外观候选如何投票成运动槽

参考候选 `r` 与查询 `q` 的 `(x,y)` 差、查询帧在窗口内的相对时间 `α` 构成一条**假设位移/速度**：首帧候选近似 `(q-r)/α`，尾帧候选近似 `(r-q)/(1-α)`；靠端点极短时间差的速度不稳定，以 `geometry_reliability` 降权。每条票的强度来自外观 softmax 权重、查询 Token 的纹理分数、Top-16 熵的清晰度及时间基线可靠性。这是“候选对应假设投票”，不是先把全图色块直接聚类。[候选几何和票权](../data/demo0_v11/core.py)

每帧把这些**全图 Token 的 Top-16 候选票**一起拟合固定 **6 个运动槽**，做 10 次软 EM：

- `H0` 槽模型只有二维平移 `(v_x,v_y)`；
- `H1` 槽模型是 `v(p)=a·p+(v_x,v_y)`，多一个以归一化图像中心位置 `p` 为变量的统一 scale-rate `a`，近似透视缩放中的局部径向场，**不是**完整透视投影、深度或遮挡模型。

EM 按速度残差给每条候选票对 6 槽的 softmax 责任，再按票权重拟合各槽参数。每帧从当帧票重新估计，随后用 Hungarian 参数代价与前帧槽编号对齐，可做参数平滑。编号连续只是模型参数对齐，不等于物体身份被准确追踪。[槽拟合代码](../data/demo0_v11/core.py)

**槽个数有固定限制 6；槽大小没有最小/最大 Token 数、连通区域、质量或面积限制。** 软概率中一个 Token 可以同时属于多个槽（6 槽概率和为 1）；网页白边界与视频着色用 `argmax` 给它一个硬编号，拒绝 Token 则不进入白边界。一个槽可跨多个不相连物体；多个同运动物体也会合并。这个设计符合“运动假设”而非“物体实例”。若以后希望一个槽尽量对应一个物体，需另外考虑连通性、外观/深度边界、实例数自适应与槽面积先验；强行规定大小也可能把真实大背景或小物体切错，不能直接加固定阈值。

## 3. 票如何反馈候选、置信度与拒绝

EM 后，每条候选的残差拟合度、周围 8 邻域的颜色边缘感知槽概率、前帧槽概率经相邻光流变形后的时间先验，以及槽总体质量，分别以 log 项加到原相似度 logits，再 softmax 重新给候选权重。`P1`：H0，无空间/时间/拒绝；`P2`：H1；`P3`：H1+空间；`P4`：H1+空间+时间；`P5`：P4+拒绝+稀疏 mask。时间先验用 **DIS 光流从真实当前帧和前一帧计算**，这是离线真实视频条件；未来只有首帧的生成初期不能照用这条真实帧光流。[P1–P5 生效参数](../data/demo0_v11/config.json)、[时间先验读取](../data/demo0_v11/pipeline.py)、[DIS 光流计算](../data/demo0_v11/core.py)

当前网页的 `confidence` 是一条**人工组合分数**：`0.24×最高候选权重 + 0.20×(1-候选熵) + 0.20×运动残差拟合 + 0.16×空间一致 + 0.20×最高外观分数强度`，再乘 `0.25+0.75×纹理分数`，截到 `[0,1]`。`reject_probability=1-confidence`，**不是基于数据标签训练/校准的概率**。P5 若 `confidence<0.18` 则拒绝，所有稀疏候选 mask 为 false；不拒绝时只在原序 Top-8 内筛出重新加权后 `weight≥0.035` 的候选，至少选择 Top-8 中一个最大者。mask 是保存的布尔候选表，**没有实际接入 VACE 的 Value/attention**。[组合分数与稀疏门控](../data/demo0_v11/core.py)

首帧 F/FL 查询首帧自己、FL 尾帧查询尾帧自己时，代码会强制自匹配候选权重和置信度为 1；这些端点查询不能作为运动追踪精度证据。一般当前帧的候选没有手工预置正确位置，但受外观、运动模型及真实相邻帧时间先验影响。[端点自匹配代码](../data/demo0_v11/core.py)

## 4. 这是不是当前查询技术的最佳实践

“全库余弦 Top-K → 多候选运动一致性 → 无匹配/遮挡处理”是合理的**可解释基线**，但不存在对所有视频、所有目标通用的“最佳实践”。手工 SIFT+颜色在纹理、尺度、遮挡与重复图案上有已知局限；当前置信度未校准，运动槽数固定，H1 也只是简化缩放。更先进的方法根据任务使用不同信息：LoFTR 的两图上下文特征与粗到细密集匹配旨在处理低纹理区域；TAPIR 的逐帧匹配加时间细化并估计位置不确定性/遮挡；CoTracker 联合跟踪很多点，利用共同轨迹强化遮挡处理；DINO-Tracker 使用语义特征加视频内适配。这些各有训练数据和成本，不可直接声称一定替换 VACE Token 更好。[LoFTR 原论文](https://openaccess.thecvf.com/content/CVPR2021/html/Sun_LoFTR_Detector-Free_Local_Feature_Matching_With_Transformers_CVPR_2021_paper.html)、[TAPIR 原论文](https://openaccess.thecvf.com/content/ICCV2023/papers/Doersch_TAPIR_Tracking_Any_Point_with_Per-Frame_Initialization_and_Temporal_Refinement_ICCV_2023_paper.pdf)、[CoTracker 原项目](https://github.com/facebookresearch/co-tracker)、[DINO-Tracker 原项目](https://dino-tracker.github.io/)

与本项目目标直接有关的优化工作，按依赖顺序是：

1. 在同一视频/同一 Token 几何下分别测外观 Top-K、候选权重和真实运动跟踪误差；取得 MC 可读的世界位置/深度/实例真值或少量人工可复核标注。没有真值时网页框“看着对”无法校准概率。
2. 用真实 VACE 的 VAE latent、条件分支 hidden、指定主干层 Q/K 分别做相似度与可重复性对照；不能把普通视频自注意力里高噪声的首帧 `x` Token 当作干净参考图特征。
3. 处理候选歧义：双向匹配、循环一致性、首/尾一致性、遮挡/不可见独立输出、候选多峰而非强迫唯一对应；尤其对纯色天空，不应把“附近的漂亮框”当唯一物理对应。
4. 运动模型从全帧固定 6 个 `translation/scale` 扩展到可按证据增减的背景/深度层/局部仿射或相机补偿模型，同时设置无匹配分支；空间先验只在足够证据时启用。
5. 在生成场景重新定义**可在线获得**的时间先验，不能用真实未来视频相邻帧的 DIS 光流；最后再考虑以候选分布指导 VACE 的某层注意力，仍需允许当前帧自身/近邻/全局必要信息。

这些是待设计和测量的方向，本文没有改任何参数或实现。
